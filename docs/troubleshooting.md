# うまくいかないとき

「ログインできない」「API キーが違うと言われる」は、原因がまったく別の 2 つです。
ここでは何が起きているかと、切り分けの順番を書きます。

---

## 1. 「ログインできない」

### 1.1 ログインの仕組み（DSH 本体）

DSH のアカウントログインは、ブラウザの**ポップアップ**を使います。

```
設定 → Models → ログイン
  └ window.open("about:blank")           … 空のタブを先に確保
      └ authorize_url を開く               … DeepSeek の認可画面
          └ 認可 → リダイレクト
              └ http://127.0.0.1:<port>/oauth/callback?code=…&state=…
                  └ Host が code を交換し、認証情報を保存
```

- コールバックは **Host のループバックアドレス**に戻ります。そのためログインは
  **スマホ単体モードでのみ**成立します。PC の Host につなぐリモートモードでは、
  リダイレクト先が PC の `127.0.0.1` になってしまい、スマホからは到達できません。
  （リモートモードでは PC 側で API キー / アカウントを設定してください。）
- ログインの待ち時間は **10 分**です。放置すると期限切れになります。
- 完了の検知は Host からの状態通知で行うので、認可後にアプリへ戻れば自動で
  「ログイン済み」になります。認可画面を閉じてしまったら、もう一度押してください。

### 1.2 アプリ側の前提

WebView がポップアップを開けないと、ログインは**押しても何も起きず**、10 分後に
期限切れになります。アプリはこのために
`setSupportMultipleWindows(true)` と `WebChromeClient.onCreateWindow` を有効にし、
ポップアップ側にも同じ `WebViewClient` を付けています（1.2.0 以降）。

それでも開かない場合:

1. ダイアログがブロックされていないか（「リンクをコピー」で PC やブラウザに貼る回避策あり）
2. 端末が省電力モードで Host を止めていないか（通知から Host の稼働を確認）
3. 認可画面は出るが戻ってこない → 単体モードかどうかを確認（メニューの表示が
   「このスマホで動作中」なら単体モード）

## 2. 「API キーが違う」と言われる

### 2.1 その表示の意味

DSH はモデル提供元の **HTTP 401 / 403** をまとめて `AUTH` に分類し、
`API key is invalid`（日本語 UI では「API キーが無効です」相当）と表示します。
つまりこの文言は **「キーが無い」ではなく「キーはあるが拒否された」** という意味です。

| 表示 | 内部の状態 | 意味 |
| --- | --- | --- |
| API key is invalid | `AUTH` | キーはあるが、提供元が 401/403 を返した |
| （生のメッセージ） | `MISSING_CREDENTIAL` | キーが未設定 |
| （生のメッセージ） | `INVALID_CREDENTIAL` | キーが空文字・不正な文字を含む |
| ログインが必要です | `ACCOUNT_SIGN_IN_REQUIRED` | アカウント未ログイン |
| サインアウトされました | `ACCOUNT_SIGNED_OUT` | アカウントの認証が失効した |

### 2.2 よくある原因と直し方

1. **キーが端末に無い / 別の端末のもの**
   資格情報は端末の `$DSH_HOME/.credentials.yaml` にだけ保存されます。PC で設定した
   キーはスマホには引き継がれません。単体モードの「設定 → Models」で入れ直します。
2. **入力が壊れている（スマホ特有）**
   モバイルキーボードの自動大文字化で `sk-…` が `Sk-…` になったり、貼り付け時に
   前後の空白・改行が混ざると 401 になります。アプリはキー入力欄に
   `autocapitalize="none"` / `autocorrect="off"` を付け、送信前に前後の空白を落とします。
   それでも駄目なら、一度 PC のメモ帳などで整形してから貼り直してください。
3. **古いキーが `.env` から読まれている**
   DSH の資格情報の解決順は
   `.credentials.yaml` → 環境変数 → `<作業ディレクトリ>/.env` → `$DSH_HOME/.env` です。
   作業ディレクトリは `/sdcard/DSH`（ファイルアクセスを許可した場合）なので、
   そこに古い `DEEPSEEK_API_KEY=…` を書いた `.env` が残っていると、意図しないキーが
   使われることがあります。`/sdcard/DSH/.env` を確認してください。
4. **リモートモードで PC 側のキーが失効している**
   この場合、エラーはスマホではなく PC の Host が出しています。PC 側で確認します。
5. **アカウントログインの期限切れ**
   `ACCOUNT_SIGNED_OUT` は上の表のとおり別の文言です。ログインし直してください
   （アカウントのトークンは自動更新されません）。

### 2.3 ログで確かめる

Host のログはアプリ専用領域の `files/home/logs/host.log` にあります。デバッグビルドなら
次のように読めます（秘密の値そのものは出ません）。

```pwsh
adb shell run-as dev.tatudrag0n.dshmobile tail -n 200 files/home/logs/host.log
```

`[llm-deepseek-api-key]` の行に、どの資格情報（マネージド / 環境変数 / `.env`）が
選ばれたかが出ます。

## 3. 「ホストの認証が失効しました」

これは**モデルの鍵とは無関係**です。Host のセッション（トークン → Cookie）が
切れたときに出ます。

- Host を再起動するとセッションは失効します。アプリは 401 を検知すると
  自動でペアリング画面に戻るようにしています（1.2.0 以降）。
- PIN は Host の起動ごとに変わります。PC のコンソール、または
  `~/.dsh/mobile-pair.json` の `pin` を見てください。
- 何度も間違えると 10 分間ロックされます（回数は接続元ごと）。

---

## 4. リモートモードで繋がらない

- PC 側が `127.0.0.1` だけで待っていると、スマホからは繋がりません。
  `dsh-mobile.ps1` か `dsh web --host 0.0.0.0` で LAN に公開してください。
- 接続先は `192.168.0.166:3080` のように**ポートまで**入れてください
  （省略時は 3080 を補います）。
- スマホと PC が同じ Wi-Fi にいること、PC のファイアウォールで 3080 が開いていることを
  確認してください。VPN や Docker の仮想アダプタのアドレスが表示されることがあるので、
  その場合は正しい LAN アドレスを手入力します。

---

## 5. 既知の制限

- **未送信のまま起動を繰り返すと、空のセッションが増えます。** DSH はセッションに最初の
  メッセージが入るまで永続化しないため、次回起動時に前回のセッションを開き直せず、
  新しい空セッションを作ります（一覧に空の行が並びます）。1 度でもメッセージを送れば
  永続化され、以後は同じセッションが開き直されます。DSH には削除の RPC が無いため、
  増えた空セッションはアーカイブ（一覧から隠す）で整理してください。
- **リモートモード（PC の Host に接続）ではアカウントログインは使えません**（1.1 節）。
  ログインは Host のループバック callback に戻る仕組みで、PC の 127.0.0.1 には
  スマホから到達できないためです。PC 側で API キーを設定してください。
- **単体モードのログインとセッションの記憶は `http://127.0.0.1:3080` に紐づきます。**
  3080 が埋まっていて別ポートで起動した場合（起動ログの `(fallback)`）はオリジンが
  変わるため、ログイン状態とセッションの記憶がリセットされます。
